# ESC GOLD SERVER

Flask / WebSocket сервер SignalDesk: веб-панель отправителя, клиенты и ключи доступа, рассылка торговых сигналов, история, ответы клиентов и уведомления безопасности. MT5 работает в Windows-клиенте или в отдельной VPS-ферме; самому серверу сигналов MT5 не требуется.

## Текущий сервер: 130.49.163.172

- Генератор и API: https://admin.130.49.163.172.sslip.io:4115/
- WebSocket: `wss://ws.130.49.163.172.sslip.io:4116/ws`.
- Панель фермы: https://farm.130.49.163.172.sslip.io:4117/
- Исходники сервера: `/root/mttrader/admin`; база, пароли и ключи: `state/` внутри этого каталога.
- Исходники фермы: `/root/mttrader/client`, [отдельный приватный репозиторий](https://github.com/Cantinier/esc-gold-farm).

На этом VPS уже работает общий Caddy в `/backends/proxy`. Он обслуживает HTTPS 4115/4116/4117 и другие проекты. Внутренние порты генератора — **127.0.0.1:14115 и 127.0.0.1:14116**. Не назначайте ему внешние 4115/4116: их занимает Caddy. Файл `compose.override.yaml` подключает шлюз к общей сети `backends-edge`; он относится к настройкам VPS и исключён из Git.

### Первичная установка на текущем VPS

Эти команды нужны для новой установки; на уже работающем VPS используйте раздел обновления ниже.

```bash
sudo -i
install -d -m 700 /root/mttrader
git clone https://github.com/Cantinier/esc-gold-server.git /root/mttrader/admin
cd /root/mttrader/admin
bash scripts/install-docker.sh
bash scripts/deploy.sh
```

Ответы установщику: адрес `127.0.0.1`, порт админки **14115**, порт WS **14116**, затем токен бота рассылки и ID канала. Токен вводится скрыто; никаких редакторов `.env` не требуется. Далее:

```bash
bash scripts/install-shared-proxy.sh
cat state/publisher.token
```

`install-shared-proxy.sh` предназначен именно для текущей схемы VPS: общий Caddy `/backends/proxy`, Docker-сеть `backends-edge` 172.30.90.0/24, Caddy 172.30.90.2. Скрипт сохраняет исходные конфигурации Caddy в файлы `.before-mttrader`, дописывает только сайты проекта, проверяет конфигурацию и открывает 4115–4117/TCP. При добавлении новых портов контейнер общего Caddy кратко пересоздаётся; остальные сайты и сертификаты сохраняются. Он не устанавливает второй nginx на 80/443. На другом VPS используйте обычную установку ниже и свой HTTPS-прокси.

### Обновление текущей установки

```bash
sudo -i
cd /root/mttrader/admin
bash scripts/update.sh
```

Скрипт сам получает `origin/main`, сохраняет резервную копию и пересобирает сервер. Каталоги `state/`, `backups/`, `.env` и `compose.override.yaml` остаются на VPS. Порты повторно задавать не нужно. Старый сервер 150.237.76.98 отключён; его не следует запускать параллельно с новым, иначе боты будут конкурировать за Telegram updates.

### Подключение нескольких ферм

Каждой ферме задайте указанные выше публичные HTTPS/WSS-адреса и пароль отправителя. Счета подключаются с индивидуальными ключами и привязкой устройства. Публикация из веб-панели и распознанный сигнал из Telegram проходят через один обработчик и рассылаются всем подключённым клиентам. Отдельным VPS не нужен общий диск или база с генератором. Один клиентский Telegram-бот должен обслуживаться одной фермой; для следующей независимой фермы нужен отдельный бот. Сохранённые старые сигналы при переподключении не воспроизводятся.

## Развёртывание на Ubuntu 22.04 / 24.04

Команды выполняются в root-сессии VPS (`sudo -i`). Клонируйте публичный репозиторий через HTTPS:

```bash
git clone https://github.com/Cantinier/esc-gold-server.git
cd esc-gold-server
sudo bash scripts/install-docker.sh
sudo bash scripts/deploy.sh
sudo cat state/publisher.token
```

Скрипт `deploy.sh` сам задаст вопросы в терминале:

1. **Адрес прослушивания** — `0.0.0.0` для доступа по IP с других устройств или `127.0.0.1` для доступа только с VPS через HTTPS-прокси.
2. **Порт админки** — по умолчанию `4113`.
3. **Порт WebSocket для клиентов** — по умолчанию `4114`; должен отличаться от порта админки.
4. **Токен Telegram-бота** — при первой установке, ввод скрыт. Enter позволяет пока пропустить Telegram.
5. **ID канала** — если введён токен: числовой ID вида `-100…` либо `@имя_канала`.

Введите ответ и нажмите **Enter**. Пустой ответ оставляет значение в квадратных скобках: при первом запуске это `127.0.0.1`, `4113` и `4114`, при повторном — сохранённые настройки. Неверный адрес, порт или совпадающие порты скрипт попросит ввести заново. Файл `.env` создаётся автоматически; редактор открывать не нужно. После ответов скрипт собирает и запускает сервер.

Чтобы изменить только настройки без запуска, выполните `sudo bash scripts/configure.sh`. Для применения запустите `sudo bash scripts/deploy.sh --non-interactive`: он использует уже существующий `.env` без вопросов. Остальные настройки в `.env` сохраняются. Скрипт обновления `update.sh` также использует сохранённые настройки и не задаёт эти вопросы. При первом обновлении старой установки с единственным PORT установщик запросит два отдельных порта; старый порт будет предложен для админки.

Последняя команда показывает начальный пароль отправителя только вам. Войдите в веб-панель и смените его кнопкой «Сменить пароль». Секреты генерируются на VPS, не включены в исходники и не выводятся скриптами. Последующие запуски не заменяют существующие ключи и базу.

По умолчанию оба порта слушают `127.0.0.1` для работы за HTTPS reverse proxy. Для прямого доступа укажите `0.0.0.0` в ответе на вопрос об адресе; панель будет на `http://IP:4113/`, WebSocket на `ws://IP:4114/ws`. При таком подключении HTTP/WS не шифрует пароль, ключи и сигналы. Для доступа через интернет настройте HTTPS/WSS и проксирование Upgrade для WebSocket. Скрипты не меняют firewall, существующие сервисы или порт 443. Docker публикует оба порта через собственные правила: ограничивайте доступ также firewall провайдера.

Админка и её API доступны только на ADMIN_PORT. На WS_PORT доступны /ws, /api/positions/closed и /health; панель и административные API там возвращают 404. Nginx направляет оба порта в один процесс Flask, поэтому список подключённых клиентов остаётся общим. Flask напрямую наружу не публикуется.

В Windows-клиенте укажите **порт WebSocket**. Отчёты статистики автоматически отправляются на тот же клиентский порт, поэтому пересборка клиента не требуется. При HTTPS/WSS проксируйте клиентский порт вместе с /api/positions/closed, а не только /ws.

## Обновление и резервные копии

```bash
sudo bash scripts/update.sh
sudo bash scripts/backup.sh
sudo bash scripts/restore.sh /absolute/path/to/state-TIMESTAMP.tar.gz
sudo docker compose logs --tail 100 -f
sudo docker compose ps
```

Обновление получает `origin/main`, делает резервную копию и собирает новый образ. При локальных изменениях исходников оно останавливается. Резервное копирование ненадолго останавливает сервер для согласованной копии SQLite, затем запускает его. Соединения WS восстановятся клиентами; сделки MT5 это не закрывает. Новые сигналы в период остановки не принимаются.

Архивы `backups/` содержат секреты и данные клиентов: храните их отдельно от Git с ограниченным доступом. Восстановление заменяет состояние и `.env`, сохраняя предыдущие данные в `backups/pre-restore-*`. Используйте только доверенные архивы этого сервера. Восстановление старой копии возвращает старые пароли, ключи и привязки; проверьте их после восстановления. Схему БД следует восстанавливать вместе с совместимой версией кода. Для отката кода используйте сохранённый commit и повторите deploy; автоматического отката миграций нет.

## Перенос существующего сервера

Не запускайте новую копию на том же порту одновременно со старой. Остановите старый relay, сделайте копию его каталога `relay/state`, перенесите содержимое в `state/` нового проекта и задайте владельца `10001:10001`. Затем запустите deploy. База `published.sqlite3` и оба файла `.token` должны переноситься вместе. Исходные файлы токенов нужны для запуска даже после смены пароля в панели. Действующий сервер автоматически не переносится при публикации этого репозитория.

## Клиенты и безопасность

В панели создайте клиента и передайте ему выданный ключ подключения. Совместимый Windows-клиент использует протокол 3: подписывает одноразовый запрос сервера ключом Ed25519. Первое успешное подключение привязывает устройство; одновременно допускается одна сессия клиента. Ключ Windows хранится под защитой DPAPI. Старые клиенты без подтверждения устройства отклоняются.

Значок 🔔 показывает уведомления о попытках второго подключения, несовпадении устройства и ошибках подтверждения. «Сбросить устройство» отключает сессию, удаляет привязку и выдаёт новый ключ доступа. Обычный перевыпуск ключа сохраняет привязку. Эта защита не заменяет TLS и не гарантирует защиту от администратора клиентского компьютера.

## Telegram

### Администраторы в личных сообщениях

В настройках Telegram заполните **«TG ID администраторов»**: положительные числовые ID через запятую, например `123456789, 987654321`. Пустое поле отключает личные уведомления и меню. Каждый администратор должен сначала открыть бота и отправить `/start`.

После принятия команды сервер ставит в очередь личное уведомление каждому администратору: что отправлено и сколько WS-получателей. Это подтверждение рассылки, а не исполнения сделки в MT5. Повтор той же команды не создаёт повторных уведомлений. Ошибки личных отправок видны в Telegram-журнале админки; при неизвестном результате автоматический повтор не выполняется.

Кнопка **«Активные сигналы»** (также `/signals`) показывает по три сигнала на странице, кнопки «Назад», «Далее», «Обновить» и удаление каждой записи. Меню работает даже при выключенном мониторинге канала и выключенных публикациях в канал. Доступ есть только у настроенных ID и только в личном чате. Кнопки привязаны к конкретному администратору; изменение списка администраторов или токена аннулирует старые кнопки.

**«Удалить» в текущих сигналах и в Telegram удаляет запись, но не закрывает ордера/позиции в MT5.** Для закрытия используйте «Закрыть весь сигнал». Удаление сохраняет защиту от повторного исполнения того же ID. Старые Telegram-кнопки не удаляют сигнал, уже перенесённый в историю. При удалении последнего элемента страницы список возвращается на доступную страницу.

### Чтение канала → WebSocket

В Telegram-настройках включите **«Читать канал и отправлять события в WebSocket»** и сохраните. Мониторинг использует сохранённые токен и канал, работает на сервере даже при закрытой странице и не зависит от галочки исходящих публикаций. После обновления существующей установки мониторинг по умолчанию выключен.

Фильтр распознаёт следующие сообщения целиком (регистр не важен):

```text
SELL LIMIT XAUUSD
4185 - 4186

Take profit 1: 4179.58
Take profit 2: 4168.65

стоп 4193.74
```

BUY/SELL, XAUUSD/XAGUSD, необязательное LIMIT, одна цена либо диапазон входа, 1–20 TP. Допускается заголовок «новый сигнал:». Цены, направление и порядок тейков проверяются так же, как при публикации из админки. Посторонний текст или неполные поля не исполняются.

- «Закройте первый тейк профит», «Закройте второй тейк профит» — `terminate_tp`. Поддерживаются слова от первого до десятого, а также номера 1–20.
- «Поставить безубыток!» — `breakeven_signal` по всем частям выбранного сигнала.
- Ответ на сообщение указывает исходный сигнал. Без ответа используется последний принятый сигнал канала, включая отправленный из админки. Если указанный сигнал неизвестен, удалён, находится в истории либо у него нет нужного тейка — команда отклоняется; к другому сигналу она не перенаправляется.

Входящие события проходят общий механизм публикации и рассылаются всем WS-клиентам, включая случай нуля получателей, но **обратно в Telegram не публикуются**. Собственные сообщения бота исключены. ID события детерминирован по боту/каналу/сообщению; повторная доставка и перезапуск не открывают повторные сделки. Offset и результаты распознавания хранятся в SQLite. Панель Telegram и журнал действий показывают принятые, пропущенные и отклонённые сообщения.

Читаются только новые `channel_post` из выбранного канала, опубликованные после включения мониторинга и не старше 120 секунд. История до включения и правки сообщений не исполняются. После отключения/смены канала/токена отсчёт начинается заново. При перезапуске сохраняется offset; устаревший остаток очереди пропускается. Принятая рассылка не означает исполнение MT5.

Бот должен быть добавлен в канал. Используется [Telegram Bot API getUpdates](https://core.telegram.org/bots/api#getupdates): у токена должен быть только один процесс чтения, без активного webhook. При конфликте мониторинг показывает ошибку; существующий webhook автоматически не удаляется. Если этим ботом пользуется другая система, используйте отдельного бота. Настройка исходящих сообщений описана ниже.

Кнопка **Telegram** вверху админки открывает настройки, многострочный редактор произвольного сообщения и журнал последних 30 отправок. Токен можно заменить, ID канала изменить, публикацию выключить. Пустое поле токена при сохранении оставляет действующий токен. Сервер никогда не возвращает его в интерфейс. Боту нужны права администратора канала на публикацию сообщений.

При первичной установке параметры сохраняются в `state/telegram.json` с доступом только владельцу и импортируются в SQLite при первом старте. Далее источник настроек — база данных: установка и перезапуск не перезаписывают изменения из админки. Токен не включается в Git, `.env`, браузерное хранилище или логи. Резервные копии `state/` содержат секреты Telegram и требуют защиты.

Принятый `open_order` автоматически публикуется в формате SELL/BUY, инструмент, вход, Take profit 1…N, стоп. Команды `breakeven_signal` / `breakeven_tp` публикуют «Стоп в БУ», `terminate_signal` / `terminate_tp` — выход из сигнала или соответствующей части. Это сообщение о команде отправителя, не подтверждение исполнения в MT5. Технический ID сигнала в Telegram не отображается. `modify_tp` не создаёт Telegram-публикацию.

Telegram работает независимо от числа WS-клиентов. Очередь сохраняется в SQLite вместе с принятым сигналом; повтор того же ID не создаёт вторую публикацию. Срок ожидания отправки — 120 секунд, после чего запись помечается устаревшей. Telegram-ошибка не отменяет и не задерживает WebSocket-рассылку. Изменение настроек отменяет ожидающие отправки; уже начатая отправка может завершиться со старыми параметрами.

При сетевой ошибке или перезапуске во время отправки результат может быть неизвестен: автоматических повторов нет, чтобы избежать дублей. Проверьте канал перед ручной повторной отправкой. История показывает принятие Telegram API, а не прочтение подписчиками. Произвольный текст (1–4096 символов) отправляется без HTML/Markdown-форматирования по [Telegram Bot API sendMessage](https://core.telegram.org/bots/api#sendmessage).

API администратора: GET `/telegram`, POST `/telegram/settings` с `{enabled, token, channel}`, POST `/telegram/message` с `{id: UUID, text}`. Все требуют авторизации отправителя. Повторный ID произвольного сообщения с другим текстом отклоняется.

## События

Пример тела POST `/signals` (авторизация отправителя `Authorization: Bearer PASSWORD`):

```json
{
  "event_type": "open_order",
  "event_body": {
    "id": "caa7498b-4f0b-4823-8bea-a70cc906e229",
    "side": "SELL",
    "symbol": "XAUUSD",
    "entry": [4185, 4186],
    "take_profits": [4179.58, 4168.65, 4156.53],
    "stop_loss": 4193.74
  }
}
```

`entry` — одна цена или диапазон, инструменты XAUUSD/XAGUSD, направление BUY/SELL. Сервер рассылает всем подключённым клиентам, допускает ноль получателей и добавляет срок действия 120 секунд. Лоты и символы брокера выбирает Windows-клиент. Успешная публикация не означает исполнения сделки. Повторная отправка сохранённых событий при переподключении не выполняется.

Команды: `terminate_signal`, `terminate_tp`, `modify_tp`, `breakeven_signal`, `breakeven_tp`. Тело содержит новый UUID `id`, исходный `signal_id`; команды отдельного тейка — `tp_index` от 1, изменение TP — `new_tp`. Ответы клиентов приходят как `signal_status`.

Сервер рассчитан на один процесс Gunicorn с потоками (32) и до 20 клиентов. Не увеличивайте число workers/реплик: реестр подключений находится в памяти процесса.

## Статистика закрытых позиций

Откройте `/statistics` (также ссылка «Статистика» в панели отправителя) и войдите с паролем отправителя. Таблица показывает email, счёт и брокера, номер позиции, инструмент, направление, объём, цены входа/выхода, TP/SL, прибыль, комиссию, своп, сборы и итоговый PnL. Поиск — по email или номеру счёта; даты закрытия и фильтры — время истории MT5 у брокера, без добавления часового пояса браузера, конечная дата включительно. Итоги считаются по всем отфильтрованным позициям отдельно для каждой валюты. Страница содержит до 100 строк с пагинацией.

Нужен Windows-клиент со сбором статистики. После подключения MT5 и авторизации WS он проверяет закрытия примерно раз в 10 секунд. Номер счёта должен совпадать с указанным в карточке клиента. Учитываются полностью закрытые позиции этого счёта, включая ручные и закрытия по SL/TP; частичные закрытия объединяются после полного выхода. Цены входа и выхода усредняются по объёму. TP/SL — последние доступные уровни, неизвестные значения передаются как `null`. Поддерживается используемый приложением hedging-счёт; перевороты netting-позиций не агрегируются.

История запрашивается с перекрытием ±24 часа относительно часов Windows, чтобы охватить смещение часов брокера и восстановить недавние пропущенные закрытия. При первом запуске могут появиться недавние позиции до запуска клиента; вся старая история не импортируется. Полностью закрытая позиция отправляется после двух одинаковых чтений истории с интервалом не менее 5 секунд по локальным часам. Время сделки не сравнивается с UTC Windows. Курсор истории и очередь сохраняются в SQLite профиля Windows; после перезапуска чтение продолжается с сохранённого времени. Ошибки связи вызывают повторную отправку через 30 секунд. Повторы не создают дополнительные строки. Автоторговля для отправки статистики не требуется. Данные являются отчётами клиента, а не прямой выпиской сервера у брокера.

Метки `opened_at` и `closed_at` сохраняют исходные значения истории MT5. Для отображения используется UTC-форматирование как способ сохранить цифры часов брокера; это не утверждение, что брокер работает в UTC. Старые записи автоматически отображаются по тем же правилам, без изменения сохранённых сумм и меток. У разных брокеров время может различаться.

### REST API

`POST /api/positions/closed` принимает JSON полностью закрытой позиции:

```json
{
  "account": "123456", "broker": "Broker-MT5", "trade_mode": 2,
  "position_id": "98765", "symbol": "GOLD", "side": "SELL", "volume": 0.01,
  "entry_price": 4185, "close_price": 4179, "sl": 4193, "tp": 4179,
  "profit": 6, "commission": -0.1, "swap": 0, "fee": 0, "net_profit": 5.9,
  "currency": "USD", "opened_at": 1791954000, "closed_at": 1791954600,
  "reason": 5, "magic": 26101201, "deal_ids": ["101", "102"]
}
```

Авторизация: `Authorization: Bearer <ключ клиента>`, `X-Report-Time: <Unix seconds>` и `X-Device-Signature: <base64 Ed25519 signature>`. Подписывается UTF-8 строка `SignalDesk-report-v1\n<timestamp>\n<sha256 исходных байтов JSON в hex>`. Допуск времени — 5 минут; устройство предварительно привязывается через WS. Email определяется сервером, передавать его не нужно. WS `auth_success` содержит `trading_account` для проверки счёта клиентом.

Ответ: `201 {"accepted":true,"duplicate":false}` для новой позиции, `200` с `duplicate:true` для идентичного повтора. Конфликтующий отчёт того же клиента/счёта/брокера/режима/позиции — `409`. Неверный формат/счёт — `400`; неверный ключ — `401`; неверная подпись/время — `403`. Хранение — таблица `closed_positions` в существующем `state/published.sqlite3`, включённая в обычные резервные копии.

`GET /api/statistics?search=123&from=2026-10-01&to=2026-10-31&page=1` требует пароль отправителя через существующую Basic/Bearer авторизацию. Возвращает `rows`, `total`, `page`, `page_size`, `totals` (по валютам).

### Команды из Telegram-канала

- `Закройте все ордера` — отменить отложенные ордера всех сигналов клиента; открытые позиции сохранить. Событие `cancel_all_orders`.
- `Закройте все позиции` — отменить отложенные ордера и закрыть позиции всех сигналов клиента. Событие `terminate_all_signals`.
- `Передвиньте стоп на 4124` — изменить SL ордеров и позиций всех сигналов клиента, сохранив TP каждой части. Событие `modify_all_sl`, поле `new_sl`. Ответ на сообщение не ограничивает область действия.

Массовые команды не требуют выбранного сигнала и затрагивают только локально привязанные сигналы текущего счёта, включая сигналы, удалённые из админки. Ручные сделки вне сигналов не затрагиваются. `signal_id` массовой команды равен её `id` и служит идентификатором отчёта, а не фильтром сделок. Повторная доставка того же ID не исполняется повторно. Команды управления на ферме выполняются также при паузе новых сигналов. В Windows для исполнения должна быть включена автоторговля.

Входящие команды канала повторно в канал не публикуются. Результат исполнения зависит от подтверждения MT5; ошибки отдельных сигналов не останавливают обработку остальных. Старые версии клиентов необходимо обновить для новых типов событий.


Фраза **«Ушли в БУ»** в любом месте нового сообщения канала отправляет `terminate_all_signals`.
Регистр и повторные пробелы/переносы не важны. Клиенты проверяют все свои сигналы,
отменяют оставшиеся отложенные ордера и закрывают оставшиеся позиции по рынку.
Ответ на конкретный сигнал не ограничивает действие. Это завершение торговли по сигналам,
а не перенос стопа; посторонние ручные сделки не затрагиваются. Фраза имеет приоритет
над остальным содержимым сообщения. Сообщение обратно в канал не дублируется.


### Входы LIMIT и смещение
Без слова LIMIT все ордера сигнала открываются по середине диапазона.
С LIMIT входы распределяются равномерно; параметр «Смещение входов от границ, %»
(0–50%, по умолчанию 0) сужает диапазон с обеих сторон на указанную долю исходной ширины.
Например, 4096–4097 и 20% дают 4096.2 / 4096.5 / 4096.8 при трёх тейках.
Для BUY порядок привязки к тейкам идёт от верхнего входа к нижнему, для SELL — наоборот.
При одном тейке или смещении 50% используется середина. Единственная цена не смещается.
JSON open_order поддерживает необязательное булево поле `event_body.limit`; отсутствие означает false.
Правило более выгодной рыночной цены сохраняется. Параметр действует только на новые сигналы.
Для новой логики обновите Windows-клиент; старые версии не поддерживают признак LIMIT в JSON.

Команда канала `Стоп на 90` (или `Стоп на 90,5`) равнозначна `Передвиньте стоп на 90`: устанавливает SL для всех ордеров и позиций по сигналам клиента, в том числе если SL отсутствовал. Команда `Поставить безубыток!` теперь устанавливает середину исходного диапазона сигнала; ответ выбирает сигнал, иначе выбирается последний. Фактический вход клиента не используется. Сервер добавляет `signal_midpoint` в команды breakeven_signal/breakeven_tp для поддержки ранее открытых сигналов. Обновите ферму и Windows-клиенты.
